# Project Ops Cordis 通用插件方案

状态：2026-09-08 已按用户授权实施为本地 0.3.0。下文保留设计依据；当前可用接口与安装步骤以 CORDIS_INTEGRATION.md 为准。已实现通用 Cordis 服务与 Harness 适配，Skill/MCP 不属于本轮范围。
核验基线：`1255b67656df4bdd5843c1ef28008c8616b67691`，分支 `codex/project-ops-stability-20260906`。

## 目标与兼容边界

以 Cordis 插件为交付与组合单元，让同一套任务发现、规划和验证逻辑可供接入了兼容 Cordis 运行时及服务适配的 Agent 宿主使用；原版 Harness 保持完整原生执行体验。安装入口按宿主提供，能力按实际可用接口声明，不能宣传“任意 Agent 安装后都拥有完整功能”。Skill 与 MCP 不属于本轮实施主线。

问题：当前 Bundle 无法直接在任意 Agent 上运行，添加 Markdown 也不能改变这一点。
原因：当前使用的是 `@deepseek-ai/cordis`，入口还依赖 Harness 的 fs、tools、jobs；Agent 指引通过 Harness systemPrompt 注册。仅遵循 name/inject/apply 形状不能证明其他 Cordis 发行版与服务兼容。
影响：其他宿主即使下载了包，也没有工具注册和执行生命周期接入。
推荐方案：保留 Cordis 插件生命周期，抽出独立服务契约，将 Harness 专属对象转换放在适配层，并提供随包接入文档。具体 Cordis 发行版和版本须逐一验证。

## 功能与交付结构

| 接入方式 | 计划提供的能力 | 必要条件 |
| --- | --- | --- |
| Harness 原生 Bundle | 发现、规划、执行、收集、验证、能力搜索 | 当前 Cordis 入口及已验收的原生 Tools/Jobs/FS 组合 |
| 其他兼容 Cordis 宿主 | 按实际服务提供发现、规划及执行验证能力 | 兼容运行时、工具暴露与项目读取适配；完整执行另需原生执行生命周期适配 |
| 未接入 Cordis 的 Agent 宿主 | 暂不支持直接安装执行 | 需宿主提供 Cordis 集成桥接；仅安装 npm 包或读取 Markdown 不足以启用 |

Cordis 负责插件组合、服务依赖与生命周期；项目执行仍交给宿主原生能力。宿主缺少受信执行与取消接口时，不自行启动进程作为兜底，也不增加新的任务调度器。

最小内部拆分：

- 共享核心：任务声明、影响图、计划摘要、结果归一化、门禁规则；移除对 Harness 专属类型的依赖。
- Cordis 插件层：通过明确的服务依赖注册 Project Ops 能力；适配器名称使用插件命名空间，避免将不同宿主的同名 fs/tools/jobs 误认为同一接口。
- Harness 适配：保留现有工具名称、安装入口、原生审批/沙箱/Jobs 行为；通用入口不在导入时加载 Harness 专属模块。
- 指引：以一份工作流源文件生成宿主短提示和随包参考文档，避免两套流程漂移。

先维持独立仓库与现有包名；评估同一 canonical tgz 提供通用 Cordis 与 Harness 兼容入口。保留现有入口默认行为，避免现有用户升级后缺失服务。Markdown 描述安装和 Agent 使用契约，不承担插件执行功能。

## 数据结构与接口需求

以下是设计语义；实际已导出的类型为 ProjectOpsHost、ProjectScope、RunArgs、CollectArgs、ExecutionResult、ExecutionReceipt 等，参见接入文档。不要按下列概念名猜测工具 API：

- `HostCapabilities`：宿主/适配版本、项目读取、前台执行、后台任务、取消、可信结果和证据新鲜度能力；区分不可用、未知和已实测。
- `TaskInvocation`：仅接受重新发现的任务 ID、声明摘要及固定调用结构，不接受任意 command 文本。
- `ExecutionRef`：适配器生成的不透明执行引用；内部绑定宿主身份、项目、任务、输入快照和原生 job ID。它不是新的任务队列。
- `ExecutionEvidence`：结构化退出状态、证据来源、输入快照标识、执行引用。模型提供的结果摘要不得升级成宿主可信证据。
- 宿主适配接口：执行声明式任务、读取结构化结果、取消原生任务、校验归属。只提交接口需求，不修改 Harness 核心或其他插件。

缺少执行适配时不暴露可执行的 run/collect；仅有调用方自报回执时不能宣称已完成宿主验证。能力搜索也只覆盖当前适配器真实可见的能力。

## 新电脑上的文档与首次使用

- `README.md`：先按宿主选择安装方式，再列实际已验收版本；不要求读者理解维护历史。
- `docs/AGENT_USAGE.md`：统一发现→规划→执行→收集→验证契约；明确只有依赖任务成功完成后，才能启动其依赖方。按顺序启动后台任务不能保证这个条件。
- 后续新增安装指南：给出 Harness 与首个其他 Cordis 宿主的真实安装、服务组合、Agent 工具暴露、启用/重启、卸载和回滚步骤；适配开发者另有服务契约文档。
- 后续新增只读能力诊断：说明宿主、插件、项目根、工具可见性、执行器/依赖检测结果，以及可用功能。检测不到的内容明确为未知，不自动安装依赖或修改用户配置。
- 首次验收：工具实际可见 → 列出预置样例任务 → 生成计划 → 经宿主执行 → 获取可信结果 → 门禁。仅文件已安装、提示已注册均不算完成。

## 稳定性优先项

以下是实施前的内存复现结果。0.3.0 已增加自动任务过滤、顶格列表支持、内容快照和受信回执绑定回归：

1. 问题：`verify` 会选入 `lint:fix`、`test:update`、`test:watch`。
   原因：按名称 token 判定用途，没有区分修复、更新快照或常驻任务。
   影响：自动检查可能改文件或一直运行。
   推荐方案：用途与执行特性分开建模；保守默认排除已识别的修复/更新/常驻模式，并允许项目明确声明。名称分类不能当作只读安全保证，宿主审批与沙箱仍有效。
2. 问题：`pnpm-workspace.yaml` 的 `packages:` 下顶格 `- packages/*` 被静默忽略。
   原因：解析器先判断顶格新字段并退出，再尝试匹配列表。
   影响：同一样例缩进列表发现两个任务，顶格列表只发现根任务，两者均无诊断。
   推荐方案：采用有界、结构化的 workspace 配置解析；不支持的形式必须产生诊断，覆盖列表、排除规则及遍历上限回归。
3. 问题：同一路径源码修改后，旧成功回执仍能通过门禁。
   原因：计划摘要绑定路径列表和声明，未绑定源码内容快照。
   影响：合成成功回执在源码从值 1 改为值 2 后仍返回 `passed`；此复现不代表实际任务执行通过。
   推荐方案：规划、执行前后及验证绑定受信输入快照，覆盖未提交/未跟踪内容、删除及相关配置；超出覆盖范围或无法建立快照时报告证据不足。仅 HEAD、时间戳或模型提供的 hash 均不足以证明新鲜度。

## 实施顺序与验收

1. 基础修复：解决以上任务分类、workspace 静默漏项和证据新鲜度问题；先设计快照覆盖边界，再改变回执版本。确保旧客户端不会将新证据不足状态解释为通过。
2. 功能完善：抽出最小共享服务契约，保留 Harness 兼容入口，实现 Cordis 通用插件层、能力诊断和宿主接入指引。验证加载、卸载、重载时工具与提示正确注册和释放。首个其他 Cordis 宿主通过真实接入验收后，再声明对应兼容性。
3. 测试优化：运行 Harness 回归、打包及隔离 DSH_HOME 安装/运行/卸载；增加无开发目录和 node_modules 链接的干净运行环境验收。每个目标宿主验证工具实际调用、拒绝、取消、超时、重载与过期回执。

smoke:package 保留快速原生组合验收；新增 smoke:clean 在新目录安装真实 Cordis 和固定版本 Harness 依赖，不引用开发目录 node_modules。首次 npm 原生宿主 peer 自动解析超时，后续在明确安装固定 peer 的测试环境使用 legacy-peer-deps；最终结果与平台范围记录于 HANDOVER.md。

完整验收证据见 HANDOVER.md。不会将自定义 Cordis 验收桥接描述为所有 Agent 产品均通过。未推送、未打 tag、未发布 Release。
